# SAC Agent 隔离集成验证：真实工作流、工程故障与证据范围

> **本文用途**：说明公开 Skill 框架在专业 SAC Agent 中曾如何接入、验证了哪些路径，以及哪些结果可以由公开代码复现。它是经整理的技术摘要，**不是原始 HTTP 收据、客户运行数据或完整私有代码**。发布该摘要和源码前仍须取得相应授权。

## 1. 为什么单独写集成验证？

通用治理的单元测试可以证明请求契约、审批和代码分支符合预期，但不能证明实际系统中的 Agent、SAC Actor、HTTP 适配、数据库事务、Redis 会话与只读模型审查能够正确配合。

这也是本项目经历的一个关键教训：早期主链 HTTP E2E 显示通过，部分解释实际走的是模板降级，未覆盖真正的模型能力。因此后续不只检查 HTTP 状态码，还检查真实执行路径、回执、数据库状态和期望组件是否真正调用。

## 2. 运行环境与验证边界

历史最终隔离验证采用：

- **真实冻结 SAC Actor**：使用本地冻结策略网络执行推理；不是用公开 Fixture 替代 Actor。
- **监听中的 HTTP 服务**：真实 Agent / Backend 请求链路，而不是直接调用单元函数。
- **隔离 MySQL 8 / Redis 7**：新的 TEST_ONLY 命名空间，验证状态、会话、过期与恢复。
- **合成业务 Profile、模拟遥测和设备 Mock**：不连接真实客户、电池、设备或生产环境。
- **RAG 关闭**：这轮未证明有证据的实时知识检索场景。

因此更准确的结论是：**完成定义范围内的 SAC 专业系统隔离集成验证**；不等于真实终端生产验收，也不等于公网租户认证已完成安全审核。

## 3. 集成工作流和状态一致性

```text
用户消息 / 确认动作
         │
         ▼
       AI Service / Agent 状态机
         │
         ├──── 读请求 / 会话：Redis（非权威投影）
         │
         ▼
    Backend / SAC Actor（真实模型推理）
         │
         ▼
    Simulator + FinalValidator
         │
         ▼
    Candidate / PlanComparison
         │
         ▼
    Risk Gate（确定性，PRE_APPROVAL）
         │
         ├── 只读 Review：不得修改 Gate、Plan、DB
         │
         ▼
    HITL PendingSession（用户确认）
         │
         ▼
    PRE_ACTIVATION：读最新权威状态
         │
         ▼
    Backend CAS + 幂等键 / 执行回执
         │
         ▼
    MySQL：原 ACTIVE → SUPERSEDED
           新 Candidate → ACTIVE
```

关键不变量：在测试作用域中 `ACTIVE_COUNT = 1`；请求不得直接控制 PCS，不得跳过 Validator 和用户确认；旧审批不能在新候选参数或新活动计划状态下复用。对于重复请求，应返回同一已完成动作的回执，而非第二次激活。

## 4. 四个最有代表性的真实故障

### E06：已成功激活，但重复确认返回 422

**现象**：第一次确认已完成激活，第二次以新的请求追踪标识重复确认时，被旧的激活前检查挡成 `422 RISK_PREACTIVATION_BLOCK`。数据没有重复写入，但 API 幂等语义不正确。

**原因**：会话确认状态与“已完成业务操作的结果回放”没有充分区分。执行成功后若直接重走激活前 Gate，会遇到候选生命周期已变化的正常状态。

**修复**：在请求身份、原审批绑定、候选权威状态与原回执一致的条件下，返回原 Backend 回执；不再发送第二次 `activate` POST。并发冲突仍由后端 CAS 处理。

**验证**：重复确认返回原回执；新 Trace 中没有第二次激活请求；MySQL 记录和最终活动状态未被二次改变。

### E09：Backend 真正停机时返回非 JSON 500

**现象**：后端不可用，Agent 边界把原始异常暴露为非结构化错误，无法给上层稳定的失败契约。

**修复**：将传输失败映射为结构化 JSON `502 BACKEND_UNAVAILABLE`；业务状态不改变，失败即阻断，禁止靠过期会话继续激活。

**验证**：真实停止后端服务获得结构化 502；恢复后合法会话可继续按授权路径激活。

### 约束摘要缺失：最大放电功率 0.5 kW 未进入 Review

**现象**：用户提交的 0.5 kW 限制已经存在于后端结构化 `UserConstraintSet.constraints`，但旧版解释数据投影读取的是扁平字段，导致 LLM 看不到这条限制。

**根因**：数据契约映射遗漏，不是提示词不够好。

**修复**：在数据适配层将约束列表投影为解释可用的结构化摘要，保留原真实值；**没有为了修复数据缺失而修改冻结 Champion / Candidate Prompt**。

**验证**：约束进入实际 HTTP 模型输入，两版冻结 Prompt 都收到正确事实。

### E01：合法 PASS 路径原本没有真正覆盖

**问题**：此前检查过 REVIEW / BLOCK 等情形，却缺少合法低风险候选通过真实 Actor、Gate、人工确认并在数据库激活的完整证据。

**解决**：选取满足现有策略的测试候选，保持 Gate 阈值不变，覆盖 PASS → 用户确认 → 前置复核 → Backend 写入的真实路径。

**验证**：真实 Actor、HTTP、Validator、Gate、确认与隔离 MySQL 激活均实际发生；PASS 不意味着跳过人工确认。

## 5. 验收指标及严格定义

| 维度 | 历史结果 | 统计范围 |
| --- | ---: | --- |
| 通用治理公开回归 | **330/330** | 当前开源代码可重新运行的 pytest，不是内部 E2E 请求数 |
| SAC 既有回归 | **88/88** | 独立 SAC 套件，原始测试不全部包含于公开包 |
| 定向单测 | **24/24** | 针对上述集成问题与边界的独立测试 |
| 最终路径及只读不变量 | **21/21** | 最终核验口径；初次尝试存在一次模板回退失败，历史记录保留 |
| Agent HTTP 请求记录 | **38 条** | 包含冷启动、重试、审批、错误与恢复；不是 38 个独立成功任务 |
| 测试作用域中 ACTIVE_COUNT | **1** | 所检查测试作用域的 SQL 快照 |
| 越权激活 / 多 ACTIVE / 设备写 | **0** | **仅限被测案例**，不是普遍安全证明 |

同一 HTTP 请求记录的整体 P95 约 **12.58 秒**，包含多种请求类型，不是“每次 LLM 只花 12.58 秒”，也不是压力负载容量证明。真正的 Prompt A/B Review P95 见 [评测说明](07_evaluation.md)。

## 6. 公开版本和内部验证到底有什么关系？

| 能力 | 当前 GitHub 公共资产 | 内部隔离集成历史 |
| --- | --- | --- |
| 通用治理源码 | 有，330 项测试可复现 | 同样治理逻辑经历 SAC 适配 |
| SAC 专业接口与风险策略 | 有 | 真实 Backend、Actor、HTTP 接入 |
| SAC 演示 | 合成 `LocalSACFixtureBackend` | 真实 Actor 与数据库事务 |
| 原始 HTTP / SQL / Redis 回执 | 不提供 | 历史测试环境中保留 |
| 原始模型权重、设备及真实客户数据 | 不提供 | 设备亦为 Mock，无真实客户生产部署 |
| 验证结果 | 有声明与方法摘要 | 有私有原始记录，不由 GitHub 单独复现 |

如果团队或面试官要求独立复现实验，可以公开地重现**通用 330 项、4 个合成示例和资源校验**；真实 SAC 完整复现需要有权使用对应模型、后端、数据库和私有测试资产，不能仅靠公开 ZIP 完成。

## 7. 建议的面试讲解顺序

首先解释为什么高风险操作要由确定性 Gate 判断；其次说明为什么审批后仍需执行前复核和后端 CAS；然后用 E06、E09 和 0.5 kW 事实遗漏说明真实集成发现了什么；最后用分层测试说明单元通过不等于整机成功。
