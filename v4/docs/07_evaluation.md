# 分层评测与 A/B 方法：工程正确性、模型质量、真实集成分别验证

> 本文记录已完成的测试及其证据边界。**本公开 ZIP 可以独立复现通用治理测试与合成演示；Benchmark112 的真实模型调用及 SAC 内部 HTTP 收据不随包发布。** 未运行的新实验不能用作既有成绩。

## 1. 先定义测什么，不能只看“PASS 数量”

| 层级 | 测试对象 | 判定方式 | 当前结果 |
| --- | --- | --- | --- |
| L1：类型契约 / 单元测试 | 请求 Schema、Policy、Approval、CAS 前置检查、文件校验 | pytest 与确定性断言 | **330/330**（公开包） |
| L2：通用场景 | 配置变更、科研参数、SAC 合成适配、自进化演示 | 运行示例与结构化回执 | **4/4**（合成） |
| L3：专业业务回归 | SAC 领域行为、幂等、错误降级、约束映射 | 内部独立套件 | **88/88＋24/24**（历史） |
| L4：真实系统集成 | SAC Actor、HTTP、Validator、HITL、MySQL/Redis | 事件路径与最终数据库状态 | **21/21** 最终路径/不变量（历史） |
| L5：LLM Prompt 对照 | Champion vs Candidate 的解释质量 | 相同情境配对 A/B、匿名模型评审、统计分析 | **112 对**（历史） |

330、88、24 是不同层级的测试，不相加为“442 条真实端到端成功”。21/21 是最终路径与只读不变量核验，不能改写成 21 次独立完整用户任务。38 条 HTTP 请求包含重试和恢复，并不是 38/38 成功率。

## 2. 测试数据从哪里来：优先按失败机制，而不是让 LLM 随机出题

工程测试优先提取真实故障和要求，例如审批重放、执行前状态变化、跨用户访问、后端不可用、只读审查误称已激活等。为每一类定义初始状态、关键输入、必须事件、禁止事件与最终不变量。LLM 可以帮助生成表达变体，但不能自动把自己生成的判断当成权威 Gold。

### 2.1 四种常用测试设计

| 方法 | 示例 | 目的 |
| --- | --- | --- |
| 最小对照 | 只改变 `expected_active_plan_id` 一项，观察 Gate 是否阻断 | 确认决策来自关键变量 |
| 状态边界 | 待审批→已审批→状态漂移→拒绝 | 覆盖有状态工作流 |
| 负向安全案例 | 只读 Review 尝试调用 `activate` | 确认能力边界不能被提示词改写 |
| 故障注入 | 真实停机 Backend，再恢复 | 验证 fail-closed 与恢复语义 |

重要的不是多次重复一个模板，而是用不同前提、不同错误机制暴露代码和集成的薄弱环节。

### 2.2 样本独立性与划分

对模型类任务，必须区分开发样本、回归样本和保留样本。若同一物理情境衍生两个不同问法，不能随意把它们拆成互相独立的训练与保留样本；应该以共享情境为分组单位，避免数据泄漏和虚高的置信度。

公开的 `docs/evolution/claim_synthetic_cases.jsonl` 包含 **88 条合成声明核验回归用例**，用于验证声明与权威执行状态之间的一致性；它们独立于 Benchmark112，不属于实际模型回答或生产任务样本。

## 3. Benchmark112 如何构造：完整可讲述的设计

```text
14 类审查机制
      │ 每类设计 4 组模拟物理条件
      ▼
56 组模拟调度情境
      │ 每组构造 2 种自然语言问法
      ▼
112 条问题（112 对新旧 Skill）
      │ 同一个问题，分别注入同一组冻结事实
      ├── Champion Prompt → 112 条真实 LLM 回答
      └── Candidate Prompt → 112 条真实 LLM 回答
                             ▼
                   224 条 Review 回答
                             ▼
           匿名配对模型评审 + 28 对换序复评
                             ▼
                  家族级差值与自助重采样
```

**14 类机制**包括经济解释、SOC 说明、约束、风险、没有足够证据时的边界和显式注入等审查维度。56 组不是 56 位真实用户，而是“共享一套模拟调度条件”的独立场景组；每组两道问法不是两个独立物理客户样本。

**使用了什么真实代码？** 调度父计划由 StubActor 构造；Simulator、Comparator、FinalValidator、Risk Gate 使用真实 SAC 代码；Review 调用真实 DeepSeek LLM。这是“真实模型＋模拟业务情境”的离线 A/B，不能称为 112 次真实 Actor 生成的任务。

## 4. 配对为什么比各跑一组更合理？

两个 Prompt 必须看到同一问题、同一权威事实和相同的业务情境，否则回答差异会混入业务数据变化。固定模型调用条件、Prompt 内容和包哈希以后，再生成两套回答并在评审时匿名显示为 A/B，降低已知版本带来的倾向性。

但是匿名不能消除位置偏差、篇幅偏好和模型自身不稳定性。因此冻结 28 对进行反向顺序复评，并保留不同意结果。

| 评审结果 | 数量 |
| --- | ---: |
| 主评审 Candidate 获胜 | 87 |
| 主评审 Champion 获胜 | 17 |
| 平局 | 8 |
| 28 对换序后结论相同 | **17/28** |
| 位置校正后 Candidate / Champion / 平局 / 不确定 | **84 / 10 / 7 / 11** |

此结果说明模型评审倾向于 Candidate，但**不是人工投票胜率，也不是线上任务成功率**。开发过程中可进行人工定性查看；这里的百分比仍是冻结模型评分口径，不把定性查看换算为人工统计指标。

## 5. 自进化主要实验数字

| 评测维度 | Champion | Candidate | 差值 |
| --- | ---: | ---: | ---: |
| 经济解释覆盖 | 57/112 = **50.89%** | 106/112 = **94.64%** | **+43.75 个百分点** |
| SOC 解释覆盖 | 62/112 = **55.36%** | 107/112 = **95.54%** | **+40.18 个百分点** |
| 输出字符数均值 | 约 749 | 约 1,536 | 回答更长 |
| Review P95 延迟 | **13.58 s** | **18.56 s** | 增加约 4.98 s |

这里的“覆盖”测量的是是否满足评审器定义的解释维度；**覆盖更多不自动等于事实更准确、用户更满意或成本收益增加**。候选的额外回答长度和延迟是真实工程代价，不能省略。

按 56 组共享物理情境进行 **2,000 次分组 Bootstrap（自助重采样）**，估计两版覆盖差值的 95% 区间：

- 经济解释差值：**+33.93～+53.57 个百分点**；
- SOC 解释差值：**+29.46～+50.89 个百分点**。

这是当前合成场景和评分器条件下的统计不确定性，不代表生产用户总体区间。历史自动评分还存在少量事实性争议信号，需要分开对待，不能直接写成全部事实准确。

## 6. 安全与质量必须分层，不能用覆盖率冲抵越权

推荐将指标分成互相独立的四组：

1. **业务安全**：越权调用、审批重放、跨用户访问、多 ACTIVE、未执行误称执行成功；这些是独立安全阻断条件。
2. **事实与证据**：断言是否有 Validator / Backend / 可信知识来源支持；没有证据时主动说明不足。
3. **解释质量**：约束、收益、SOC、风险和下一步操作是否说明清楚。
4. **系统开销**：延迟、长度、调用失败和资源成本。

候选解释覆盖较高，并不意味着无须验证事实性、执行权、安全回归和发布策略。`evolution/quality_gate.py` 的评测输入必须区分目标、回归和保留集；结果最多是 `NEEDS_REVIEW` 或 `REJECTED`，不会自动发布。

**历史实际发布状态**：Benchmark112 Candidate 没有执行正式 Evolution Quality Gate，也没有正式晋升，`FORMAL_EVOLUTION_GATE=NOT_APPLIED`，`RC1_READY=NO`。公开合成示例验证的是代码路径，而非这次历史 Candidate 的晋升。

## 7. SAC 内部 HTTP 集成测试的统计边界

最终真实隔离集成记录包含 **38 条 Agent HTTP 请求**，最终 **21 项路径和只读不变量通过**。有一次早期 Review 模板回退失败，后来重测真实模型通过；原失败保留，不用成功重跑抹去。

单次请求 P50≈126.89ms、P95≈12578.49ms 的汇总含冷启动、审批、错误、恢复、Review 等异构路径，不能作为独立模型服务 P95 或高并发压测成绩。隔离 MySQL 的所测作用域 `ACTIVE_COUNT=1`，不安全激活、多 ACTIVE、设备写入为 0，限于这些测试，不是生产安全保证。

四个实际案例与故障修复详见 [SAC 集成报告](10_sac_integration_validation.md)。

## 8. 在本仓库如何复现公开证据？

```bash
python -m pip install -e ".[dev]"
python -m pytest -q
python scripts/validate_skills.py
python scripts/sync_assets.py --check
python -m agent_governance_portfolio verify
python -m agent_governance_portfolio demo generic_change_request
python -m agent_governance_portfolio demo research_workflow
```

这些命令不需要真实模型 Key、MySQL、Redis、设备或 SAC 权重。运行结果证明公开包可执行及现有合成测试通过，**不能重跑 112 对历史模型响应，也不能还原企业内部 HTTP 验收**。

## 9. 研究参考：为什么这样设计

- [Anthropic：Demystifying Evals for AI Agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：不同评测器分别处理执行结果、代码不变量和语义质量；失败案例适合发展为长期回归集。
- [ToolSandbox](https://arxiv.org/abs/2408.04682)：评测有状态工具执行和中间/最终里程碑，说明单靠最终答案不足以证明任务正确。
- [SkillsBench](https://arxiv.org/abs/2602.12670)：提示/Skill 可能出现负迁移，应比较新旧版本和回归损失；本项目未运行其官方基准。
- [AgentDojo](https://arxiv.org/abs/2406.13352)：提示注入应在工具和不可信来源构成的环境中评价；本项目的显式输入注入子集不能等同于其完整威胁覆盖。

外部研究是方法参考，不是对本框架的认证。来源与差异集中整理在 [参考资料](references.md)。
